# Salami roadmap and design decisions

Working notes for bringing the Salami slice-and-view application up to a usable
state. Phases A, B, D, E and F are done; C is done for the acquisition task and
for the milling task's *viewing* settings, with pattern geometry still on the
Milling tab. The slice pattern is settled (a thin rectangle) and the volume is
picked by dragging a box on the preview. The SenseAI acquisition task runs
end to end with reconstruction. The single biggest remaining gap for real runs
is still drift correction.

As of 2026-10-23 the basic loop works on hardware, and attention is turning to
experiment setup and UI clean-up.

For how the thing is structured today, see
`fibsem/applications/salami/README.md`. This document is about what is left and
why the choices were made.

## Working on this

Use the conda environment with `fibsem` installed editable (`senseai` on the
original dev machine). Do **not** use the Enthought AutoScript environment even
if it is first on `PATH` — it lacks `psygnal` and other core dependencies, and
installing them there risks upgrading numpy underneath AutoScript and breaking
the microscope bindings.

```bash
python -c "import psygnal, fibsem; print(fibsem.__file__)"   # sanity check
python -m pytest tests/salami -q                             # no microscope needed
```

`fibsem/microscopes/simulator.py` provides a `DemoMicroscope`, so most of the
application can be exercised without hardware. Files under `**/qtdesigner_files/`
are generated by `pyuic5` from the sibling `.ui` file — edit the `.ui`, not the
Python.

## Goal for the first milestone

Define the basic imaging and milling parameters in the UI, set a slice count,
press Run, and get an alternating mill/image loop that can be stopped and
resumed.

Deliberately excluded until that works: drift correction, GIS deposition,
focus compensation, relief cuts. Those come after the bare loop runs.

Progress against it: imaging parameters are editable and can be moved to and from
the microscope, the slice volume is picked by dragging a box, and Run / Stop /
Run Next Step are wired. A five slice run on the simulator acquires and saves an
image per slice.

Two caveats on that milestone. The acquisition parameters are configured but the
**beam block is not applied during a run**, which also makes `advance_beam_shift`
inert — see Phase C, *What is left*. And nothing here has been tried on a real
sample yet: everything to date is simulator plus unit tests, so the failures that
only appear with real drift, real charging and a real block face are all still
ahead.

## Phase A — experiment lifecycle *(done)*

Fixed a data-loss bug and made resume correct.

- Constructing a `SalamiExperiment` no longer writes to disk; `initialise()`
  does, once the target directory is settled.
- Three distinct operations: **New**, **Open** (directory picker), **New From
  Protocol** (copies and re-homes; never writes to the source).
- `path` is derived from the file's actual location on load, never trusted from
  the YAML.
- Slice geometry is *derived* (`baseline + step × step_size`), not accumulated.
- Sub-step resume via `next_task_index`; `in_flight_task` flags an interrupted
  mill and asks the operator.
- `as_template()` strips stage positions and output paths.

Also fixed a core bug found on the way: `MicroscopeState.to_dict()` wrote
`stage_position: None` but `from_dict()` could not read it back.

## Phase B — worker → UI channel *(done)*

- One payload type on `workflow_update_signal`: `SalamiWorkflowUpdate` now
  carries both progress and UI actions. Previously tasks emitted a dataclass and
  the interaction helpers emitted dicts, and the slot only understood dicts — so
  anything the run loop emitted crashed on arrival.
- The slot can no longer hang the worker: `try/except/finally` always clears
  `WAITING_FOR_UI_UPDATE`.
- Progress bar and status labels driven from the update counters.
- Task skipping: `enabled` (protocol) and `skip_once` (status).

## Phase C — configuration surface *(acquisition task done; milling outstanding)*

The two dead widgets (`comboBoxTasks`, `groupBoxTaskParameters`) are wired up.
Pick a task from the dropdown, edit its parameters below.

### What landed

**Editors are generated from the config dataclasses**, not hand-built.
`ui/config_editor.py::DataclassEditorWidget` walks `dataclasses.fields()`,
chooses a control per type (checkbox / spinbox / dropdown), and recurses into
nested configs as collapsible `TitledPanel` sections. Adding a field to a task
config makes an editor appear with no UI code to touch.

`ui/task_editor.py` holds the per-task **view spec** — `exclude`, `read_only`,
`flatten`, `expanded`, `dividers`, `inject`, `hints`. That is the only thing a
new field cannot infer for itself, so a field needs an entry there only if it
should *not* be freely editable.

The acquisition task renders as:

```
Name (locked) / Description / Task Enabled
Schedule
──────────── divider ────────────
[Sync from Microscope] [Sync to Microscope]  ⟳
Electron Beam (SEM):  voltage, current, working distance
Image:                resolution, dwell time, HFW, autocontrast, integration, ...
Alignment Area / Autofocus / Autocontrast
```

**Voltage and current are dropdowns from the microscope**, via a hint naming a
`get_available_values` key (`"current"`, not `"beam_current"` — the key is the
microscope's name, not the field's). Queried per beam, using the cached wrapper
on the base class. Falls back to numeric entry when nothing is connected or the
backend reports nothing for that key, which keeps offline protocol editing
working and covers Tescan, which has no `voltage` branch.

**Microscope sync**, with the logic in `tasks.py` so it is usable headless:

```python
sync_config_from_microscope(microscope, config, acquire=True) -> MicroscopeSyncResult
sync_config_to_microscope(microscope, config, acquire=True)   -> MicroscopeSyncResult
apply_beam_settings(microscope, beam_settings)                -> list[str]
acquire_preview_image(microscope, image_settings)             -> FibsemImage
resolve_beam_defaults(microscope, config)                     -> list[str]
```

The operator's loop: tune the column live, capture it into the protocol, or push
the protocol back to see what it will do. Each direction acquires an image at the
resulting settings. The UI runs these on a worker thread and shows the shared
`_SpinnerLabel`.

**`apply_beam_settings` is the safe apply** Phase C called for — only fields that
are set, via granular setters, never the stage. See *Decisions* below for why
neither `set_beam_settings` nor `set_microscope_state` can be used.

**Two readouts:** in-plane pixel size (`hfw ÷ horizontal resolution`) and
estimated acquisition time per image, under the Image section.

**The Task Config tab no longer needs a microscope.** It was gated on a
connection only because it was going to use the live beam widgets; the generated
editors read and write the config, so a protocol can be prepared offline.

### What is left

- **Milling task editor.** The generated form covers `field_of_view`, alignment
  and acquisition settings, but *not* `stages` — a list of dataclasses the engine
  does not render, and the tab says so rather than showing a milling task that
  looks empty. Plan unchanged: push the selected task's config into the existing
  `MillingTaskViewerWidget` on the Milling tab and read it back with
  `get_config()`, which gives pattern type, geometry, milling current and the
  canvas overlay for free. Two cautions: the write-back must be guarded so a
  trench config set during setup does not land in the selected slice task, and
  the existing cross-thread `get_config()` read is already a known issue (below).
- **Make the settings take effect at run time.** `AcquisitionTask.run` still has
  `set_microscope_state` commented out, so the editor and the sync configure a
  protocol that the run does not yet apply. `apply_beam_settings` +
  `microscope.set_imaging_settings` are what it needs; this is now a small change.

  This is a **correctness gap, not just a missing feature.** `cfg.image` does
  reach the column — it is handed to `microscope.acquire_image()` — so
  resolution, dwell time and HFW are applied. The beam block is not, and
  `AcquisitionTask.apply_advance` writes `beam.shift` into exactly that block.
  It is computed correctly per step onto a runtime copy which is then thrown
  away, so **`advance_beam_shift` does nothing end to end** while defaulting to
  True. `MillingTask.apply_advance` is not affected: its runtime stages go
  straight into `run_milling_task`. The asymmetry is the trap — the mill walks
  into the block and the SEM view stays put, and nothing reports it.

  A test for this must assert on what reached the microscope (a fake recording
  `set_beam_shift` calls), not on `cfg.state.electron_beam.shift`, which is
  already correct today.
- **Experiment panel.** Slice thickness (nm), ROI depth (µm) and `n_steps` as
  three linked fields — edit any, the others follow (10 nm × 50 µm → 5000). The
  persisted source of truth stays `n_steps` + `step_size`, so no schema change.
  Total estimated runtime belongs here too, from `ImageSettings.estimated_time`
  and `FibsemMillingStage.estimated_time`.
- **Task enable / skip controls.** `experiment.task_states()` already returns the
  data, and per-task `enabled` is editable in the Task Config tab. A mid-run
  overview — all tasks, enable/skip at a glance — still argues for the Experiment
  tab. Now that Task Config works offline, the original reason for preferring the
  Experiment tab (Task Config being gated on a connection) no longer applies.

## Phase D — run controls *(done)*

- Run / Stop / Run Next Step connected, each on a worker thread mirroring
  `_on_setup_clicked`. `run_next_step()` shares a `_begin_run()` prologue with
  `run()`, so stepping by hand and letting the loop run cannot disagree about
  where the run is.
- Stop is graceful, not an abort: the loop checks between tasks, so an
  acquisition or mill already in progress finishes. Interrupting a mill part way
  would leave an unknown amount of material removed.
- While running, Next Step, Setup and the microscope sync are locked; Stop is the
  only live control.
- Milestone met: press Run, get one saved image per slice.

**Still to do:** guard structural edits during a run. Changing `n_steps` mid-run
is fine (the loop re-reads it). Adding or removing a task while `_run_step` is
iterating with `next_task_index` pointing into the list is a genuine race —
disable structural edits while `run_state == "running"`, or apply them at a step
boundary. This is why `enabled` / `skip_once` exist.

## Phase E — pages, and regions on the preview *(done)*

The window follows `autolamella/ui/AutoLamellaMainUI.py`: a `SalamiMainWindow`
shell whose central tab widget holds one whole page per tab.

- **Microscope** — `SalamiUI` embedded with its menu bar hidden; quad view plus
  the widget strip. The Experiment tab keeps status and run controls only.
- **Protocol** — three columns: experiment information, task parameters, and a
  preview of the image the last microscope sync acquired. Disabled until an
  experiment exists.
- Tab-bar corner widget carries the experiment name, New/Load buttons and the
  notification bell. Unlike autolamella's, the buttons work with no microscope,
  because a Salami protocol can be prepared offline.
- The bell only counts *workflow* events (run finished / failed, sync failed) via
  `notification_service.show`; chatter stays transient via `show_toast`. Runs
  last days, so a finished run has to still be visible on return.

**Editable regions.** Each `AutoFunctionConfig` has its own `area_of_interest`,
drawn as a draggable box over the preview and editable either there or as four
spinboxes in the form. `protocol_page.draw_rectangle` is a thin manager over the
existing `AlignmentAreaOverlay`, which already speaks normalised
`FibsemRectangle` and handles drag, resize and clamping. Several coexist on one
canvas; a region is hidden while its function is disabled.

> **Trap worth remembering:** `DataclassEditorWidget` binds each control to the
> owner object it found when the form was built. Anything writing to a nested
> config behind the form's back must **mutate** it, not replace it — assigning a
> new `FibsemRectangle` silently orphans its four spinboxes.

## The slice pattern — settled: a thin rectangle

Compared on the microscope, and the rectangle won. `DEFAULT_SLICE` is now a
`RectanglePattern`: 40 µm wide, one slice thickness tall, cutting 5 µm into the
face. It gives the three things a line could not — a `width` that means slice
width, a `height` that *is* the slice thickness, and a `point` that
`define()` actually reads, so the pattern can be placed and advanced.

**Slice thickness has one home.** `advance.step_size` is the source of truth;
`MillingTask.apply_slice_thickness` sets each stage's pattern height from it on
the per-step runtime copy, so the slab cut and the distance advanced cannot
drift apart. They are the same physical quantity — a pattern shorter than the
advance leaves unmilled material between slices, taller and it re-cuts what the
last step removed, and either only shows up once the stack is reconstructed.

Consequence to be aware of: **editing a slice pattern's height on the Milling
tab has no effect** — it is overwritten per step. Change the slice thickness
instead. If deliberate over-milling is ever wanted (cutting slightly deeper than
the advance, to avoid leaving ridges), that wants an explicit overlap factor
rather than letting the two values diverge silently.

Patterns with no `height` — a trench has upper and lower heights, a line has
none — are left alone rather than guessed at.

## The milling volume box *(done)*

A yellow box on the milling task's preview picks the volume to collect.

| Box | Binds to |
|---|---|
| position | `pattern.point` |
| width | `pattern.width` — the slice width |
| height | `n_steps × step_size` — the depth of volume to collect |

The box's height is the *whole volume extent*, not the pattern height. The
pattern is one thin slab, `step_size` tall, that walks through the box: it sits
at the bottom edge on step 0 and the top of the last slab lands on the top edge.

**Nothing extra is persisted.** The box is reconstructed from the pattern plus
`n_steps` (`tasks.milling_region_for`) and read back the other way
(`tasks.apply_milling_region`), so it redraws correctly on reload and there is
no second copy of the volume to fall out of step with the protocol.

`ImageGeometry` owns the conversion, including the y flip — frame fractions have
their origin top-left with y down, pattern metres have theirs at the frame
centre with y up.

**Slice thickness is on the slice task's form**, as a `SliceVolumePanel` above
the generated fields. It edits `advance.step_size`, which is experiment-level
(one volume, one thickness, shared with the acquisition task's beam-shift
advance) but is the control an operator reaches for on the task that slices.

**The slice count is always derived, never typed.** Drag the box and it follows;
change the thickness and it follows, holding the volume constant — halve the
thickness over the same block and you get twice as many slices.

Two things to be aware of:

- `n_steps` is experiment-level, so dragging the box on one milling task changes
  the whole experiment's slice count. Right for a single volume, but it edits
  something outside the task.
- The box needs a preview image to mean anything, since fractions of a frame
  become metres only via its pixel size. With no image the panel says so rather
  than drawing a box that cannot be converted.

## Phase F — the SenseAI acquisition task *(done)*

An alternative to the ordinary acquisition task: the frame is scanned by an
external scan generator through the SenseAI DLL, sub-sampled, and optionally
reconstructed. One 4-page TIFF per slice (Reconstruction / Reference / Input /
Mask); Input and Mask are the measurement and are written losslessly, so any
slice can be reconstructed again later in the SenseAI desktop app.

**The DLL and the scan generator load once per process, and never from the
task.** The DLL's source registry outlives the Python object, so a second
`SenseAI_ModuleControl` inherits the first one's sources, collides on *"source
already exists"*, and leaves a generator that was never initialised. Every step
of that failure is logged and swallowed, so it reported success and only
surfaced later as an acquisition waiting for a frame that never came.

- The SenseAI tab's *Initialise Scan Generator* builds the module and publishes
  it with `set_senseai_module`. Pressing it again adopts the existing one, and
  a module that failed to initialise is never published.
- A headless run passes its own in on `RunContext.senseai_module`.
- The task calls `require_senseai_module`, which raises if there is none or if
  it reports a `readiness_problem`. Refusing is deliberate — far easier to
  diagnose than a generator that silently never returns a frame.

Everything the task may do is per-slice: update the generator config, take the
scan external, give it back.

**The preview goes back on the workflow update, not `sem_acquisition_signal`.**
That signal is a psygnal, so handlers run in the *emitting* thread — and the
handler is the image widget, which draws on the quad-view canvas. Emitting from
the run's worker thread put Qt drawing on a non-GUI thread, which is what
produced the intermittent freeze after the first slice. The frame also needs
real metadata (`senseai_preview_image` supplies it): the widget reads
`beam_type` to pick a pane and the canvas reads `pixel_size` for its scale bar,
and a bare `FibsemImage(array)` is dropped with *"Image metadata is None"*.

**The viewer shows the reconstruction when there is one**, falling back to the
measurement when reconstruction is scheduled off or fails, with the caption
saying which. The Input page at 30% sampling is a sparse scatter of pixels —
displaying it unconditionally made a working reconstruction look like a
reconstruction that never ran.

A DLL update (received 2026-10-23) cleared the remaining
`Waited for 523ms for acquisition to finish` and `timeout waiting for scan
state` warnings that every earlier run produced.

## Later — what actually makes the data good

Roughly in priority order for real runs:

1. **Fiducial and per-slice drift correction.** `_create_fiducial` /
   `_confirm_fiducial` are stubs, so there is no alignment at all. Over a
   multi-day run this is the single biggest gap. Templates:
   `autolamella/workflows/tasks/fiducial.py` and `base.py::_align_reference_image`.
2. **Focus/WD compensation** for the receding face, beyond periodic autofocus.
3. **GIS protective cap** in setup (`fibsem/gis.py` exists), and relief cuts —
   currently trench only.
4. **Tilt / foreshortening correction** for the off-normal SEM view.
5. Persist the trench config adjusted during setup; it is currently held on the
   instance only (`experiment.trench_config`).

## Decisions made, and why

**Editing a protocol must not touch the microscope, so the stock beam widgets
are unusable here.** Every handler in `FibsemBeamSettingsWidget` calls a
`microscope.set_*` immediately on change. That is right for a live control panel
and wrong for a protocol that may be days from running — or running right now, on
a different slice. Hence the generated non-live editors. Reads are still fine:
dropdowns come from `get_available_values`, which sets nothing.

**Editors are generated from the dataclasses rather than hand-built.** The task
configs are the schema; duplicating them in widget code means every new field
needs a UI change and the two drift. Two implementation notes that are easy to get
wrong:

- `fibsem/structures.py` uses `from __future__ import annotations`, so
  `field.type` there is a string like `'Optional[BeamSettings]'`. Everything
  resolves through `typing.get_type_hints()` — the pre-existing dispatcher in
  `autolamella_task_config_widget.py` compares `annotation == bool`, which for
  those fields silently falls through to a text box.
- No field in the tree carries `metadata`, so units live in `FIELD_HINTS` keyed by
  field name. Putting them on the dataclasses would mean editing core `fibsem`
  structures for a Salami display concern.

**`ImageSettings` owns resolution / dwell time / HFW; the beam block does not.**
(This resolves Phase C's open problem.) `AcquisitionTask.run` hands
`ImageSettings` to `acquire_image`, so that is the value that takes effect. The
duplicate fields on `BeamSettings` are excluded from the editor and never written
by a sync, so there is never a question of which one wins.

**Selectable values come from the microscope, never a free number.** A protocol
storing a current the column cannot do would fail at step 0. A stored value the
column does not offer is shown as-is and labelled, rather than snapped to the
nearest supported one — a protocol written on another machine should read back as
itself.

**No "unset" entry on those dropdowns; the config is seeded instead.** Showing the
first supported value while the config still held `None` would make the form lie,
and the run would apply neither. `resolve_beam_defaults` fills unset fields before
the form is built, so what is displayed is what is stored.

**Neither `set_beam_settings` nor `set_microscope_state` can apply a protocol.**
Both are landmines, which is why `apply_beam_settings` exists:

- `set_beam_settings` forwards every field into a setter including `None`. On a
  fresh protocol almost every field is `None`; it raises by the time it reaches
  `set_scan_rotation(None)`, and on the simulator silently corrupts stored state
  before that.
- `set_microscope_state` calls `safe_absolute_stage_movement` whenever
  `state.stage_position` is not `None` — and `MicroscopeState.stage_position`
  defaults to a *non*-`None` `FibsemStagePosition` with all-`None` axes. The guard
  therefore always passes and the position reaches `movement.angle_difference`,
  which raises on `None % float`. Slice-and-view must never move the stage
  mid-volume regardless.

**Stigmation and scan rotation are never applied.** `BeamSettings.from_dict`
turns a null `stigmation` into `Point(0, 0)` rather than `None`, so the only value
the protocol can ever hold there is that load artifact — applying it would zero
the stigmator on a column the operator had just tuned. Beam `shift` *is* applied,
because `apply_advance` writes it and that is what makes `advance_beam_shift`
track the receding face.

**A sync image is a preview and is never saved**, even when `config.image.save` is
set. Writing it would drop an image into the task's output directory where it
would be indistinguishable from run data, and the protocol's `path` is only set
per-step at run time anyway.

**Sync logic lives in `tasks.py`, not the UI.** The UI is one caller; a script,
a test, and eventually `AcquisitionTask.run` are others. It also means the
interesting behaviour is testable without Qt.

**Config edits save immediately rather than behind an Apply button.** A protocol
can be edited mid-run, where a half-applied config is worse than an eagerly saved
one.

**Milling geometry is edited on the Milling tab, not duplicated in Task
Config.** Two widgets drawing patterns on one FIB canvas would need arbitration.

**"Slice width" is pattern geometry; the z-advance is experiment-level.** In an
experiment you choose a slice thickness and an ROI depth, and the slice count
follows.

**Advance is derived per step, not accumulated.** Resume lands at the right
depth, no float drift over thousands of additions, and the stored protocol stays
a clean step-0 baseline. It also means a mid-run protocol edit is picked up at
the next step boundary rather than mid-step.

**Advance applies to all milling stages, not just `stages[0]`.** A coarse+fine
slice pair has to stay on the same plane.

**`enabled` lives in the config, `skip_once` in the status.** Disabling a task
is a protocol change that should survive a resume; `as_template()` resets it so
a fault on one sample does not silently disable the task on the next. A one-shot
skip is a decision about *this* run, but still has to survive a crash — which is
exactly what status is for.

**`enabled` is separate from `schedule.end_step`.** Setting `end_step` to the
current step would also stop the task, but it conflates an operator decision
with a planned cadence and destroys any real schedule the task had.

**An interrupted mill asks rather than guesses.** An unknown amount of material
was removed. Re-running may double a slice; skipping may leave one uncut.
Neither is a safe default.

**Task `state` should hold beam settings only.** Stage position is
sample-specific and belongs in `status.sample_state`. Once Phase C applies beam
settings for real, a reused protocol carrying the old sample's stage position
would drive the stage there.

## Known issues not yet addressed

- The worker reads widget state from a background thread
  (`parent_ui.milling_task_config_widget.get_config()` in `_prep_area`).
  It works because that reads plain Python attributes, but it is a latent
  thread-safety problem. Don't extend the pattern. The sync worker deliberately
  does the opposite: it touches no widgets and reports back through
  `sync_finished_signal`, handled on the main thread.
- `utils.format_value` emits U+03BC, which a logging handler on a cp1252 console
  cannot encode. Logging swallows the error, so the entry is silently lost rather
  than crashing — but on a multi-day run the log *is* the record.
  `MicroscopeSyncResult` works around it with a separate `log_summary`; the
  underlying handler encoding is untouched and would bite anything else that logs
  a formatted value.
- `microscope.get_imaging_settings` is incomplete (its own TODO): it returns
  resolution, dwell time and HFW but not autocontrast, integration or drift
  correction. `sync_config_from_microscope` therefore captures only those three,
  which is why `SYNCED_IMAGE_FIELDS` is narrow.
- The `ParameterWidget` classes reused from
  `fibsem/ui/widgets/autolamella_task_config_widget.py` are generic but live under
  an autolamella name, so Salami imports across applications. They would sit
  better in a shared widgets module if a third caller appears.
- The generated editor does not render lists of dataclasses, which is why milling
  `stages` are absent from the Task Config tab.
- `LinePattern.define()` ignores `BasePattern.point` while `RectanglePattern` uses
  it. No longer bites the default slice, which is now a rectangle, but
  `tasks.advance_pattern_y` still handles both so a line-based stage does not
  silently fail to advance. The core classes are shared with other applications,
  so they are left alone — the inconsistency remains there for anything else
  assuming `point` positions a pattern.
- `AcquisitionTaskConfig.alignment_area` is now read by nothing and hidden from
  the editor, reserved for fiducial drift correction.
- A run applies imaging settings but not beam settings — the Phase C item above.
  Until then, Sync to Microscope before running, or the images come out at
  whatever the column was last set to rather than what the protocol says.
  (The SenseAI task is the exception: it applies its own beam block.)
- The ordinary `AcquisitionTask` still emits its preview on
  `microscope.sem_acquisition_signal` from the worker thread — the same
  cross-thread hazard the SenseAI task was moved off. It works today because
  its images carry metadata so the handler completes, but it is the same latent
  freeze and should move to the workflow update too.

## Next — experiment setup and UI clean-up

With the basic loop working on hardware, the focus moves to the parts around
it. Nothing here is specified yet; recorded so the thread is not lost:

- Experiment setup (`setup_experiment`) is still trench milling plus two stubs,
  `_create_fiducial` and `_confirm_fiducial`. Those stubs are what block drift
  correction, which remains the biggest gap for real multi-day runs.
- UI clean-up generally — the Experiment tab, task add/remove
  (`ui/add_task_dialog.py`, currently uncommitted), and the enable/skip controls
  that `experiment.task_states()` already provides data for.
